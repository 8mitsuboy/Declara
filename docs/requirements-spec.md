# Declara create_subTask 要求仕様書

## 1. 文書情報

- 文書名: `create_subTask 要求仕様書`
- 対象機能: やりたいこと入力からサブタスクを生成・表示する機能（MVPにおいて進捗管理と完了アニメーションを含む）
- 対象バージョン: MVP
- 作成日: 2026-03-01

## 2. 背景と目的

- ユーザーが「本来やりたいこと」を入力すると、実行可能な単位のサブタスクへ分解して提示する。
- ユーザーの「何から始めるべきかわからない」状態を解消し、最初の行動を促進する。

## 3. スコープ

### 3.1 対象

- 1つの入力テキストからサブタスク候補一覧を生成する。
- 生成結果を画面上に一覧表示する。
- 入力不備や生成失敗時にエラーメッセージを表示する。
- タスクの永続化（保存・同期）
- 進捗管理: ユーザーがサブタスクを完了・未完了にできること、完了状態はUIに反映され永続化されること。
- 完了時に気持ちの良いアニメーション（モーション）を表示すること。

### 3.2 非対象

- ユーザー認証
- 通知、期限管理

## 4. 利用者と利用シーン

- 利用者: 個人ユーザー（一般）
- 主なシーン: やりたいことを思いついた直後に、必要作業を短時間で洗い出したいとき
- 引っ越したい！と入力。その後アプリ側で引越しのために必要な作業を生成。住所変更、賃貸情報取集など

## 5. 用語定義

- `要求`: ユーザーが入力する「やりたいこと」の自由記述テキスト
- `サブタスク`: 要求を達成するための具体的行動単位
- `生成`: 要求テキストを分析し、サブタスク一覧を返す処理
- `進捗管理`: サブタスクの完了/未完了状態の記録と表示
- `完了アニメーション`: サブタスクを完了した際に表示される短い視覚的演出
- `MVP`: 最小実用機能を提供する初期リリース

## 6. 機能要求

### FR-01 入力受付

- ユーザーは要求テキストを入力できること。
- テキスト入力はキーボードの確定操作（Enter）または生成ボタン押下で送信できること。

### FR-02 サブタスク生成

- 送信された要求に対し、サブタスク一覧を生成すること。
- 入力前後の空白は無視して評価すること。
- 入力が空文字の場合、生成処理を行わずエラーメッセージを返すこと。

### FR-03 生成結果表示

- 生成されたサブタスクをリスト形式で表示すること。
- 各サブタスクは少なくともタイトルを表示すること。
- 生成結果がある場合、ユーザーが視認しやすい形で画面内に表示されること。

### FR-04 実行中状態表示

- 生成処理中はローディング表示を行うこと。
- 生成処理中は重複実行を避けるため、生成操作を無効化すること。

### FR-05 エラーハンドリング

- 入力不備（空文字）時は「入力を促すエラー」を表示すること。
- 生成処理失敗時は「再試行を促すエラー」を表示すること。
- エラー発生時は古い生成結果をクリアすること。

### FR-06 進捗管理（MVPに含む）

- ユーザーがサブタスクを完了/未完了に切り替えられること。
- 各サブタスクの状態は永続化され、アプリ再起動後も保持されること。
- 画面上に進捗（例: 完了数/総数やプログレスバー）を表示すること。

### FR-07 完了時アニメーション

- サブタスクを完了にした際に短い視覚的アニメーションを表示すること（例: チェックのバウンス、 confetti の簡易版など）。
- アニメーション中はUIが応答不能にならないこと。
- アニメーションは設定でオフにできること（アクセシビリティ配慮）。

## 7. 非機能要求

### NFR-01 応答性

- 生成開始から結果表示またはエラー表示まで、通常条件で 3 秒以内を目標とする。

### NFR-02 可用性/安定性

- 例外発生時でもアプリがクラッシュせず、ユーザーへ失敗理由を表示できること。

### NFR-03 保守性

- 生成ロジックはUI層から分離され、差し替え可能なインターフェース経由で利用できること。
- レイヤー境界（Presentation/Application/Domain/Data）を維持すること。

### NFR-04 テスト容易性

- ドメインユースケースはUI依存なしで単体テスト可能であること。
- 状態管理ロジックは生成処理をモック化してテスト可能であること。

### NFR-05 UX/アニメーション品質

- 完了アニメーションは短時間で滑らかに終了すること（目安: 300–800ms）。
- アニメーションは視覚過多にならないよう控えめであること。

## 8. 制約条件

- Flutterで実装すること。
- 初期MVPでは生成ロジックはローカル実装（キーワードベース）を許容する。
- 将来的にAPI/LLM実装へ差し替え可能な構成を維持すること。

## 9. 受け入れ基準（Acceptance Criteria）

### AC-01 正常系

- Given ユーザーが「結婚式に参加したい」と入力している
- When 生成操作を行う
- Then サブタスク一覧が1件以上表示される

### AC-02 空入力

- Given ユーザー入力が空文字または空白のみ
- When 生成操作を行う
- Then 入力エラーメッセージが表示され、サブタスクは表示されない

### AC-03 生成失敗

- Given 生成処理で例外が発生する
- When 生成操作を行う
- Then 再試行を促すエラーメッセージが表示される

### AC-04 実行中制御

- Given 生成処理が実行中
- When ユーザーが再度生成操作を試みる
- Then 追加の生成処理は開始されない

### AC-05 サブタスク完了とアニメーション

- Given ユーザーがサブタスクを完了マークにする
- When 完了操作を行う
- Then 完了状態が永続化され、短い完了アニメーションが表示される（設定でオフ可能）

### AC-06 進捗反映

- Given いくつかのサブタスクが完了している
- When 画面表示／更新が行われる
- Then 完了数/総数とプログレス表示が正しく反映される

## 10. 将来拡張要件（MVP外）

- サブタスク編集、削除
- 生成結果の保存（ローカル/クラウド）
- ユーザーごとの履歴、再生成、おすすめテンプレート
- LLM連携時のプロンプト最適化、セーフティ制御、コスト管理
- Then 対象サブタスクに完了アニメーションが再生される
