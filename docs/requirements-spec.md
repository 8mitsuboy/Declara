# Declara 要求仕様書

## 1. 文書情報

- 文書名: `Declara 要求仕様書`
- 対象機能: 宣言入力からタスク生成・進捗管理・完了フィードバックまでの一連の機能
- 対象バージョン: MVP
- 作成日: 2026-03-01
- 最終更新日: 2026-03-08

## 2. アプリコンセプト

### 2.1 思想

Declaraは**宣言的プログラミング**の思想をタスク管理に適用したアプリである。

- 宣言的: **What（何をしたいか）** だけ言えばいい → 「引っ越したい」
- 手続き的: **How（どうやるか）** を全部自分で考える → 「住所変更して、不動産探して...」

**ユーザーはWhatだけ宣言する。HowはAIが解決する。**

### 2.2 解決する課題

先延ばしには悪循環がある。
何をすればいいかわからない → 考えるのが面倒でやりたくなくなる → でもやらなきゃいけないから落ち込む → さらに動けなくなる。
この悪循環の起点は「中身がブラックボックスであること」にある。
Declaraはそのブラックボックスを開封し、中身を見える化することで悪循環を断ち切り、最初の一歩を促す。

### 2.3 核心的価値

1. **ブラックボックスの解消** - 宣言するだけでAIが中身を開けてくれる。先延ばしの根本原因を解決する。
2. **入力の極小化** - 意志も義務も区別なく、ただ「やりたいこと」「やらなければならないこと」を宣言するだけ。タスクを考える負担をゼロにする。

## 3. ターゲットユーザー

### 3.1 ペルソナ

先延ばし癖のある人。やりたいことはあるが「何をすればいいかわからない」が原因で動けない。

- プライベートで利用する
- やりたいことを思いついた瞬間にサッと使う
- 既存Todoアプリは「タスクを自分で考える」初動が重くて使えない

### 3.2 利用シーン

やりたいことを思いついた直後に、必要な行動を短時間で洗い出したいとき。

- 例: 「引っ越したい！」と入力 → 住所変更、賃貸情報収集、荷造りなどのタスクが生成される

## 4. ユーザーの感情フロー

| フェーズ | 行動 | 感情 | 設計への示唆 |
|---------|------|------|------------|
| 停滞 | 何もできない | 「やりたいけど何すれば...」 | ここがアプリの出発点 |
| 宣言 | 「〜したい」と入力 | 気軽にポンと | 入力UIは極限までシンプルに |
| 待機 | 生成中 | 少しのワクワク | 短く、不安にさせない |
| 開封 | タスク一覧を見る | 安心「これだけやればいいのか」 | 見通しが立つ瞬間が最大の価値 |
| 実行 | タスクを1つずつ消す | 進んでる感、小さな達成感 | 進捗の可視化が重要 |
| 達成 | 全完了 | やりきった！ | 達成感のフィードバック |

**挫折リスク**: タスクが多すぎると動けなくなる → タスク数の制御が必要

## 5. 用語定義

| 用語 | 定義 |
|------|------|
| 宣言（Declaration） | ユーザーが入力する「〜したい」という自由記述テキスト。アプリの起点となる。 |
| タスク（Task） | 宣言を実現するための具体的行動単位。AIが生成する。 |
| 生成 | 宣言テキストを分析し、タスク一覧を返す処理。 |
| 進捗管理 | タスクの完了/未完了状態の記録と表示。 |
| 完了アニメーション | タスクを完了した際に表示される短い視覚的演出。 |
| MVP | 最小実用機能を提供する初期リリース。 |

**補足**: 宣言は再帰的な構造を持ちうる。タスク自体をさらに宣言として分解し、孫タスクを生成することも将来的に可能とする。MVPでは2層（宣言→タスク）に限定する。

## 6. スコープ

### 6.1 対象（MVP）

- 宣言テキストの入力からタスク一覧を生成する
- 生成結果を画面上に一覧表示する
- 入力不備や生成失敗時にエラーメッセージを表示する
- タスクの永続化（保存・同期）
- タスクの完了/未完了の切り替えと永続化
- 完了数に応じた進捗（件数・率）の表示
- タスク完了時の視覚的フィードバックアニメーション

### 6.2 非対象（MVP外）

- ユーザー認証
- 通知、期限管理
- タスクの再帰的分解（孫タスク）

## 7. 機能要求

### FR-01 宣言入力

- ユーザーは宣言テキストを入力できること。
- テキスト入力はキーボードの確定操作（Enter）または生成ボタン押下で送信できること。
- 入力UIは極限までシンプルであること（感情フロー「宣言」フェーズ: 気軽にポンと）。

### FR-02 タスク生成

- 送信された宣言に対し、タスク一覧を生成すること。
- 入力前後の空白は無視して評価すること。
- 入力が空文字の場合、生成処理を行わずエラーメッセージを返すこと。
- 生成されるタスク数は3〜7個程度に制御すること（挫折リスクの軽減）。

### FR-03 生成結果表示

- 生成されたタスクをリスト形式で表示すること。
- 各タスクは少なくともタイトルを表示すること。
- 生成結果がある場合、ユーザーが視認しやすい形で画面内に表示されること。

### FR-04 実行中状態表示

- 生成処理中はローディング表示を行うこと。
- 生成処理中は重複実行を避けるため、生成操作を無効化すること。

### FR-05 エラーハンドリング

- 入力不備（空文字）時は「入力を促すエラー」を表示すること。
- 生成処理失敗時は「再試行を促すエラー」を表示すること。
- エラー発生時は古い生成結果をクリアすること。

### FR-06 進捗管理

- ユーザーがタスクを完了/未完了に切り替えられること。
- 各タスクの状態は永続化され、アプリ再起動後も保持されること。
- 画面上に進捗（例: 完了数/総数やプログレスバー）を表示すること。
- 進捗の可視化により「進んでいる感」を提供すること（感情フロー「実行」フェーズ）。

### FR-07 完了時アニメーション

- タスクを完了にした際に短い視覚的アニメーションを表示すること（例: チェックのバウンス、confettiの簡易版など）。
- アニメーション中はUIが応答不能にならないこと。
- アニメーションは設定でオフにできること（アクセシビリティ配慮）。

## 8. 非機能要求

### NFR-01 応答性

- 生成開始から結果表示またはエラー表示まで、通常条件で3秒以内を目標とする。

### NFR-02 可用性/安定性

- 例外発生時でもアプリがクラッシュせず、ユーザーへ失敗理由を表示できること。

### NFR-03 保守性

- 生成ロジックはUI層から分離され、差し替え可能なインターフェース経由で利用できること。
- レイヤー境界（Presentation / Domain / Data）を維持すること。

### NFR-04 テスト容易性

- ドメインロジックはUI依存なしで単体テスト可能であること。
- 状態管理ロジックは生成処理をモック化してテスト可能であること。

### NFR-05 UX/アニメーション品質

- 完了アニメーションは短時間で滑らかに終了すること（目安: 300〜800ms）。
- アニメーションは視覚過多にならないよう控えめであること。

## 9. 制約条件

- Flutterで実装すること。
- 生成ロジックはAI（Claude API）を利用する。
- 将来的に他のLLMへ差し替え可能な構成を維持すること。

## 10. 受け入れ基準（Acceptance Criteria）

### AC-01 正常系

- Given ユーザーが「結婚式に参加したい」と入力している
- When 生成操作を行う
- Then タスク一覧が3〜7件表示される

### AC-02 空入力

- Given ユーザー入力が空文字または空白のみ
- When 生成操作を行う
- Then 入力エラーメッセージが表示され、タスクは表示されない

### AC-03 生成失敗

- Given 生成処理で例外が発生する
- When 生成操作を行う
- Then 再試行を促すエラーメッセージが表示される

### AC-04 実行中制御

- Given 生成処理が実行中
- When ユーザーが再度生成操作を試みる
- Then 追加の生成処理は開始されない

### AC-05 タスク完了とアニメーション

- Given ユーザーがタスクを完了マークにする
- When 完了操作を行う
- Then 完了状態が永続化され、短い完了アニメーションが表示される（設定でオフ可能）

### AC-06 進捗反映

- Given いくつかのタスクが完了している
- When 画面表示/更新が行われる
- Then 完了数/総数とプログレス表示が正しく反映される

## 11. 将来拡張要件（MVP外）

- タスクの再帰的分解（タスクをさらに宣言として分解し、孫タスクを生成）
- タスクの編集、削除
- ユーザーごとの履歴、再生成、おすすめテンプレート
- LLM連携時のプロンプト最適化、セーフティ制御、コスト管理
- ユーザー認証、クラウド同期
- 通知、期限管理

## 12. ドメインモデル（MVP）

```
Declaration（宣言）
├── id: String
├── title: String        // 「〜したい」
├── done: bool
└── tasks: List<Task>

Task（タスク）
├── id: String
├── declarationId: String
├── title: String        // 具体的な行動
├── done: bool
└── sortOrder: int
```

将来的にはTaskがparentIdを持つ再帰構造に拡張可能：

```
Declaration
├── id: String
├── parentId: String?    // nullならルート宣言
├── title: String
├── done: bool
└── sortOrder: int
```
